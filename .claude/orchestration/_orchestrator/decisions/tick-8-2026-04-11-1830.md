## P1-4 — `scheduler-public-api` → RESOLVED (two sub-decisions)

### Sub-decision A: `CurrentDate` → **`DisplayDate`**

**Rationale (user):**

- `CurrentDate` is ambiguous (could mean today's system date).
- `DisplayDate` is the industry-standard name used by Telerik Scheduler, MudBlazor Scheduler, and Syncfusion — unambiguous "the date the calendar view is centered on."
- Avoids collision with `DateTime.Today` / `DateTime.Now` mental model.

### Sub-decision B: `TItem` with `ISchedulerAppointment` interface constraint

Public component API uses `TItem : ISchedulerAppointment` where the interface requires `Id`, `Start`, `End`, `Title`. Users implement on their own model.

**Rationale (user):**

- The `allocation-scheduler` workspace already uses a DTO pattern internally, but forcing a concrete DTO on the PUBLIC scheduler component creates a breaking coupling.
- Open-closed: users bring their own model, interface provides the shape.
- Matches the Telerik Scheduler pattern.

**Classification:** **Public API change** — orchestrator-only. Workers may NOT self-implement.

**Remediation routing:**

- Owner: `scheduler-gap-analysis` workspace (to be bootstrapped).
- Lane 1: introduce `ISchedulerAppointment` interface in `src/Marilo.Components/Scheduling/` (additive).
- Lane 2: rename `CurrentDate` → `DisplayDate` with obsoletion shim if any internal callers exist (check `allocation-scheduler` cross-refs).
- Lane 3: update spec snippets + demos + docs to use `TItem` with the interface constraint and `DisplayDate`.
- Sync areas: `source`, `spec`, `demo`, `docs`, `tests`.

## P1-5 — `scheduler-policy` → RESOLVED (two sub-decisions)

### Sub-decision A: `manual-operations.md` scope = single file covering ALL scheduler mutation operations

One file covers add, edit, delete, drag-drop, resize. Per-operation files create fragmentation that agents repeatedly get wrong. One file = one source of truth for what operations are allowed, blocked, or require confirmation.

**Location:** `docs/component-specs/scheduler/manual-operations.md` — published in spec tree.

### Sub-decision B: Per-topic policy, not per-parameter flags

Use a `SchedulerEditPolicy` record with named boolean properties grouped by concern (e.g., `RecurrencePolicy`, `DragDropPolicy`, `InlineEditPolicy`).

**Rationale (user):**

- Per-parameter flags (`AllowDrag`, `AllowResize`, `AllowDelete`, etc.) explode combinatorially and produce hard-to-document interaction rules.
- Per-topic grouping matches how `allocation-scheduler` already structures its operation permissions.
- Cleaner spec surface.

**Remediation routing:**

- Owner: `scheduler-gap-analysis` workspace.
- Files: `docs/component-specs/scheduler/manual-operations.md` (new), `src/Marilo.Components/Scheduling/SchedulerEditPolicy.cs` (new, additive), spec snippets updated to reference the record.
- Sync areas: `source`, `spec`, `docs`.
