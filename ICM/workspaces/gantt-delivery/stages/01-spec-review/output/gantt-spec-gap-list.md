### Source-ahead gaps (in code, absent from spec)

- **SRC-01 (Source-ahead):** `src/Marilo.Components/DataDisplay/MariloGantt.razor:549,564-575,670-680` — Milestone rendering (`isMilestone = taskStart == taskEnd`) produces a diamond glyph (`&#x25C6;`) inside `mar-gantt__milestone` with `aria-label="Milestone: {title}: {date}"`. Neither `overview.md`, `events.md`, `refresh-data.md`, nor `state.md` mentions milestone tasks, milestone detection rule, or the diamond visual. Also absent from `timeline/templates/task.md` inspection scope of this audit. Missing from `docs/component-specs/gantt/overview.md` and `docs/component-specs/gantt/timeline/templates/task.md`.
- **SRC-02 (Source-ahead):** `src/Marilo.Components/DataDisplay/MariloGantt.razor:550,552-555,561,657-667` — Summary-task rendering. Any node with `Children.Count > 0` is treated as a summary: bar uses `ComputedStart/ComputedEnd/ComputedPercentComplete` (bottom-up aggregation) and gains the `mar-gantt__bar--summary` CSS class. Spec never documents that parents auto-aggregate — the `events.md` example still shows a manual `CalculateParentRangeRecursive` helper, implying the user must compute it themselves. Missing from `docs/component-specs/gantt/overview.md` and `docs/component-specs/gantt/gantt-tree/data-binding/overview.md`.
- **SRC-03 (Source-ahead):** `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs` (private `GanttNode<TItem>.ComputedStart/ComputedEnd/ComputedPercentComplete`) + summary-task compute routine — the internal `ComputeSummaryValues` / bottom-up pass is documented nowhere. Callers who try to read a parent's `PercentComplete` from their own model will see stale values while the bars render aggregates. Missing from `docs/component-specs/gantt/overview.md`.
- **SRC-04 (Source-ahead):** `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs:211` — `FireStateChanged("VisibleColumns")` is raised when the column chooser toggles visibility, so `OnStateChanged.PropertyName` can take the value `"VisibleColumns"`. `docs/component-specs/gantt/state.md:63` enumerates only `"SortDescriptor"`, `"FilterValues"`, `"ExpandedItems"`, `"View"`. Missing from `docs/component-specs/gantt/state.md`.
- **SRC-05 (Source-ahead):** `src/Marilo.Components/DataDisplay/GanttState.cs:82-97` — `GanttState<TItem>` actually exposes `EditItem`, `OriginalEditItem`, `InsertedItem`, `EditField`, `ParentItem`, `VisibleColumns` as public settable properties. `state.md:43-51` only documents `SortDescriptor`, `FilterValues`, `ExpandedItems`, `View` as the Phase-1 surface and lists the others as "planned". The properties exist now; they are just not wired through `GetState()` / `SetStateAsync`. Spec should either document them as partial or acknowledge that `GanttState<TItem>` already has the fields. Missing accurate coverage in `docs/component-specs/gantt/state.md`.
- **SRC-06 (Source-ahead):** `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs:88` — `Data` is declared as `IEnumerable<TItem>` with default `Enumerable.Empty<TItem>()`. `refresh-data.md` documents `ObservableCollection<T>` reactivity but spec does not explain that source relies on `OnParametersSet`-based reference-and-count detection plus an explicit `Rebind()` for in-place mutations. The auto-detect behaviour (new reference ⇒ full tree rebuild) is only referenced obliquely. Missing expanded coverage in `docs/component-specs/gantt/refresh-data.md`.

### Spec-ahead gaps (in spec, absent from code)

- **SA-01 (Spec-ahead):** `docs/component-specs/gantt/state.md:232-239` — example code constructs `new GanttState<GanttTask> { SortDescriptors = new List<Marilo.DataSource.SortDescriptor>{ ... }, FilterDescriptors = new List<IFilterDescriptor>() { ... } }`. Source `GanttState<TItem>` has **no** `SortDescriptors` plural property and **no** `FilterDescriptors` property — it has `SortDescriptor` (singular, `GanttSortDescriptor`) and `FilterValues` (`Dictionary<string, string>`). The spec example will not compile against the current API. Missing from `src/Marilo.Components/DataDisplay/GanttState.cs`.
- **SA-02 (Spec-ahead):** `docs/component-specs/gantt/state.md:178` — example uses `Marilo.DataSource` namespace types (`FilterDescriptorCollection`, `FilterDescriptor`, `IFilterDescriptor`, `CompositeFilterDescriptor`, `Marilo.DataSource.SortDescriptor`, `Marilo.DataSource.ListSortDirection`). None of those types are consumed by `MariloGantt` — its state surface is flat strings and a dictionary. Either the source needs to adopt the richer descriptor model or the spec needs to be rewritten against the actual types. Missing from `src/Marilo.Components/DataDisplay/GanttState.cs`.
- **SA-03 (Spec-ahead):** `docs/component-specs/gantt/state.md:108` — "Filtering always resets the current page to 1, so the `OnStateChanged` event will fire twice. First, `PropertyName` will be equal to `\"Page\"`". MariloGantt has no paging model at all — it is a hierarchical tree renderer. This bullet is a stale copy/paste from DataGrid spec and does not reflect any source behaviour. Missing from `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs` (and should be removed from spec).
- **SA-04 (Spec-ahead):** `docs/component-specs/gantt/state.md:186-189` — example sets `ColumnResizable="true"` and `@bind-TaskListWidth="@TaskListWidth"`. Neither `ColumnResizable` parameter nor a two-way-bindable `TaskListWidth` / `TaskListWidthChanged` callback exists in `MariloGantt.razor.cs` — `TaskListWidth` is a plain `[Parameter] public int` with no matching `EventCallback`. Missing from `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs`. (Cross-ref: existing GAP-GANTT-S06 and GAP-GANTT-S13 cover the underlying features; this entry records the specific `@bind-TaskListWidth` usage pattern.)
- **SA-05 (Spec-ahead):** `docs/component-specs/gantt/events.md:44-46` — `TaskListWidthChanged` event is documented without a type signature, and it is not declared in `MariloGantt.razor.cs`. Source has no splitter resize path that would raise it. Missing from `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs`. (Complements GAP-GANTT-S13 — the prior record noted it; this one tags the precise spec line.)
- **SA-06 (Spec-ahead):** `docs/component-specs/gantt/overview.md:157-161` — "Gantt Parameters" table lists only `RowHeight` and `GanttToolBarTemplate`. Source exposes 30+ parameters on `MariloGantt<TItem>` plus many on `GanttColumn`/`GanttCommandColumn`/views. The overview parameter table is under-populated to the point of being misleading. This is a spec coverage gap, not a missing feature — but treated as spec-ahead because the spec still claims this table is the component parameter reference. Missing full table in `docs/component-specs/gantt/overview.md`.
- **SA-07 (Spec-ahead):** `docs/component-specs/gantt/overview.md:221,253` — references API namespace `Marilo.Blazor.Components.MariloGantt-1`. Actual source namespace is `Marilo.Components.DataDisplay`. Slug links `Marilo.Blazor.Components.MariloGantt-1` and `Marilo.Blazor.Components.GanttState-1` resolve to a non-existent API surface. Missing from `src/Marilo.Components/DataDisplay/MariloGantt.razor.cs` (namespace) or from spec cross-refs.
- **SA-08 (Spec-ahead):** `docs/component-specs/gantt/overview.md:226-228` — "Gantt Reference and Methods" table lists only `Rebind`. Source additionally exposes `GetState()` and `SetStateAsync(GanttState<TItem>?)` as `public` methods on `MariloGantt.razor.cs:1680,1708`. Overview table is missing them, even though `state.md` documents them. Missing from `docs/component-specs/gantt/overview.md`.

### Naming / structural mismatches

- **NM-01 (Naming mismatch):** Spec `state.md:232` uses `SortDescriptors` (plural, `List<SortDescriptor>`) — source `GanttState.cs:70` uses `SortDescriptor` (singular, `GanttSortDescriptor?`). Spec also implies multi-sort; source supports only single-column sort (`_sortField` single string). Escalation candidate: picking one direction (multi-sort support vs. spec rewrite) is a public-API decision for the orchestrator.
- **NM-02 (Naming mismatch):** Spec `state.md:237` uses `FilterDescriptors : List<IFilterDescriptor>` — source `GanttState.cs:73` uses `FilterValues : Dictionary<string, string>?`. Same escalation class as NM-01: adopting `IFilterDescriptor` is a type-system change with implications for `FilterRow` input parsing. Orchestrator decision.
- **NM-03 (Naming mismatch):** Spec `state.md:63` lists `PropertyName` values as `"SortDescriptor"`, `"FilterValues"`, `"ExpandedItems"`, `"View"`. Source additionally raises `"VisibleColumns"` (MariloGantt.razor.cs:211). Spec enumeration is incomplete. Same site as SRC-04 — tagged separately because it is a name-list gap rather than a behaviour gap.
- **NM-04 (Naming mismatch):** Spec `overview.md:223` uses `MariloGantt<MyModel>` in a reference example; source class is declared `public partial class MariloGantt<TItem> where TItem : class` in `Marilo.Components.DataDisplay`. The generic name differs (`TItem` vs. spec's use of a user-supplied `MyModel`) — acceptable for user-facing docs, but the namespace path in SA-07 is the real problem. Flagged here for completeness.
